What an inference server does

It turns a folder of weights and a GPU into one HTTP endpoint that many people can call at once, and keeps that GPU busy.

  1. Speaks HTTP. OpenAI-style /v1/chat/completions and /v1/responses, plus /health and /metrics. vLLM also answers Anthropic-style /v1/messages.
  2. Tokenises the prompt with the model's chat template.
  3. Schedules: at every step it decides which requests run.
  4. Manages KV-cache memory in fixed-size pages.
  5. Runs the model: one prefill pass over the prompt, then one decode step per new token.
  6. Streams tokens back and parses reasoning and tool calls.
EngineLatest release
vLLMv0.33.0, 2 Nov 2026. Wheels and images are CUDA 13.0 only, on PyTorch 2.14.
SGLangv0.5.23, 2 Nov 2026. Adds opt-in “Paged Experts” and LoRA on FP8 and NVFP4 MoE models.

Both are Apache-2.0 and do all six jobs. They differ in how they schedule, cache and parallelise. That difference is most of this guide.

The request path

Tokenisechat template
Queuewaits for a slot

Prefillwhole prompt
Decode1 token per step

Prefill reads the prompt in parallel and writes its keys and values into KV pages. Decode then adds one token per step to every running request.

Time to first token (TTFT) is queueing plus prefill. Inter-token latency (ITL) is the length of one decode step, which everyone in the batch shares.

The pearl pages on the plate belong to one request; the thread joins them in logical order. Tap any other page to follow that request instead.

Sources: vLLM docs: Optimization & tuning (TTFT, ITL), online serving. The plate is a simulation.

Continuous batching

Static batching waits for the slowest request. Continuous batching rebuilds the batch at every step: finished requests leave, waiting ones join.

vLLM gives each step a token budget. Decodes are served first; what is left goes to prefill chunks (chunked prefill is on by default). The docs' rule: a small budget such as 2048 gives better ITL, a large one better TTFT. Try it.

The KV cache: what the model remembers

Every attention layer keeps a key and a value vector for every token it has seen, so later tokens never recompute them. The cache grows by one token per decode step, per request.

bytes per token = 2 × layers × KV heads × head dim × bytes per value

For Qwen3.8-27B, from its config.json: 64 layers, but only every 4th is full attention, so 16 layers keep a growing cache. 4 KV heads, head dimension 256, stored as FP8 (1 byte).

Pink: 16 full-attention layers. Aqua: 48 linear-attention layers, which keep a fixed-size state instead.

2 × 16 × 4 × 256 × 1 B = 32,768 B
32KiB per token
× 262,144 tokens, the full context
8GiB per full-length request

Hence NVIDIA's warning that --max-num-seqs 8 with a 262,144-token limit doesn't guarantee eight full-length requests fit at once.

Sources: huggingface.co/nvidia/Qwen3.8-27B-NVFP4 config.json (64 layers, full_attention_interval 4, 4 KV heads, head_dim 256) · NVIDIA recipe (--kv-cache-dtype fp8) · dgx-spark-playbooks, playbook-vllm.

PagedAttention: memory in pages

Older servers reserved one contiguous slab per request, sized for its maximum length. vLLM's launch post measured 60–80 % of KV memory wasted that way.

PagedAttention borrows the operating system's trick: cut the cache into fixed-size blocks, hand them out only as tokens arrive, and keep a block table from each request's logical blocks to physical blocks anywhere in memory. Only the last, part-filled block is wasted: under 4 %.

On the plate each square is one block and each dot one token (16 per block here). The followed request's block table, read back live:

Blocks can be shared between requests, with reference counts and copy-on-write.

When the pages run out

If a running request needs a page and none is free, the scheduler preempts a request: it frees that request's pages and recomputes it later. The log says the sequence is preempted by PreemptionMode.RECOMPUTE mode because there is not enough KV cache space.

The docs' fixes: leave --gpu-memory-utilization unset or raise it, or lower --max-num-seqs or --max-num-batched-tokens. Unset, it now defaults to 1.0 with vLLM's extensible KV cache, which sizes itself from memory measured after warm-up.

Prefix caching vs RadixAttention

Both engines keep the KV pages of a prompt prefix they have seen before (a system prompt, earlier turns, an agent's tool list) so the next request skips prefill for those tokens.

vLLM: hashed blocks

Each full block is keyed by a hash of its parent's hash, its tokens and extras such as LoRA ID or cache_salt. Idle blocks wait in an LRU free queue until reused or evicted.

SGLang: a radix tree

A tree whose edges hold runs of tokens; LRU evicts leaves first. --schedule-policy lpm schedules for cache hits (default fcfs).

Why decoding is limited by memory, not maths

Each decode step has to stream every weight from memory once, whether it produces 1 token or 8. On a DGX Spark that read sets the pace:

273 GB/s ÷ 21.9 GB of weights ≈ 12 steps per second

So one user would see about 12 tokens/s estimate. There are two ways past the ceiling:

  • Batch: 8 users share each read and get 8 tokens per step.
  • Speculate: check several guessed tokens per read (chapter IV).
37.29tokens/s, one user

NVIDIA's measurement on a 128 GB Spark with the recipe in chapter VI: aiperf, SPEED-Bench coding prompts, 8,192 output tokens, concurrency 1, speculative decoding on. About three times the naive ceiling.

The estimate assumes the whole checkpoint is read on every step and ignores KV reads.

Sources: nvidia.com DGX Spark specs (273 GB/s) · Hugging Face file sizes, nvidia/Qwen3.8-27B-NVFP4 · NVIDIA local-ai-inference-recipes performance.yaml (measured 2026-10-19).

E2M1 has only the magnitudes 0, 0.5, 1, 1.5, 2, 3, 4 and 6. NVFP4's smaller blocks and fractional scales fit each block more closely; NVIDIA puts it at about 3.5× smaller than FP16.

Real checkpoints mix formats. NVIDIA's Qwen3.8-27B uses NVFP4 for MLP layers and lm_head, FP8 for attention, and stays within about 1.5 points of BF16 on six benchmarks (GPQA Diamond 88.92 → 88.01).

Tensor and expert parallelism

Tensor parallelism (TP) slices every layer's matrices across GPUs. Every GPU works on every token.

Expert parallelism (EP) puts whole experts on different GPUs and sends each token to the GPUs holding its chosen experts. In vLLM EP size = TP × DP; with TP = 1, attention is replicated on every data-parallel rank.

vllm serve deepseek-ai/DeepSeek-V3-0324 \
  --tensor-parallel-size 1 \
  --data-parallel-size 8 \
  --enable-expert-parallel
vLLM docs, 8 GPUs

SGLang: --tp-size, --ep-size, --dp-size. In vLLM, --enable-eplb rebalances hot experts and --all2all-backend picks the transport (DeepEP, FlashInfer NVLink, MoRI).

Sparks link over ConnectX-7 at 200 Gb/s: two or three with one QSFP cable, four through a switch. NVIDIA has a separate cluster playbook.

Sources: vLLM docs: Expert parallel deployment · docs.sglang.io server arguments · nvidia.com DGX Spark; dgx-spark-playbooks (playbook-vllm-cluster).

Speculative decoding

A small, fast draft proposes k tokens. The big model checks all k in one pass, which costs about the same as a single step when memory is the limit. It keeps the longest correct run and adds one token of its own.

When self-hosting beats an API

Host it yourself when…

  • Data must stay put. Prompts never leave the box.
  • Load is steady. The box costs the same whether it serves 1 user or 8; its GB10 has a 140 W TDP.
  • You need a pinned model. Pin image, model and code revisions and nothing changes under you.
  • Prompts share long prefixes, as agent loops and RAG do. Cache hits skip prefill.

Use an API when…

  • The model doesn't fit. Kimi K3.1 Pro's 1,561 GB of weights is about 12 Sparks of memory.
  • Load is bursty. You'd pay for an idle box most of the day.
  • One user needs speed. 37 tokens/s is good; hosted fleets on bigger GPUs are faster.
  • You can't own operations: security patches and upgrades that move flags.

Our judgement, built on numbers sourced elsewhere in this guide. Not a price comparison.

Steps 1–2: prepare, then download

Run these on the Spark itself (DGX OS, Ubuntu-based). Docker must work without sudo.

Downloads total about 26 GB. The image is public on NGC; if a pull fails with unauthorized, run docker logout nvcr.io.

Use a read-only Hugging Face token. Both models are Apache-2.0 and ungated.

Step 3: launch vLLM

NVIDIA's validated flags, exactly as in the playbook's 128 GB launch script. It binds to loopback.

  • 0.60 on purpose: at 0.85 the node hung during startup autotune, and 0.70 took nodes down on some runs.
  • Mount only ~/.cache/huggingface; the image keeps prebuilt kernel caches under /root/.cache.
  • dflash with prefix caching needs the fix in vllm#60252, which this image has.
  • Text only? Add --language-model-only to skip the vision encoder.
docker run -d --name vllm-qwen38 \
  --gpus all --ipc host --network host \
  --shm-size=16g --ulimit memlock=-1 --ulimit stack=67108864 \
  --entrypoint "" \
  -e HF_TOKEN="${HF_TOKEN:-}" \
  -v "$HOME/.cache/huggingface:/root/.cache/huggingface" \
  nvcr.io/nvidia/vllm:26.10.pre1-py3 \
  vllm serve nvidia/Qwen3.8-27B-NVFP4 \
    --host 127.0.0.1 --port 8000 \
    --kv-cache-dtype fp8 \
    --max-model-len 262144 \
    --max-num-seqs 8 \
    --async-scheduling \
    --enable-flashinfer-autotune \
    --gpu-memory-utilization 0.60 \
    --kernel-config '{"linear_backend":"nvfp4_dynamic","nvfp4_dynamic_max_tokens":16,"unquantized_linear_backend":"flashinfer_cudnn","linear_backend_per_quant":{"fp8_w8a8":"cutlass"}}' \
    --speculative-config '{"method":"dflash","model":"z-lab/Qwen3.8-27B-DFlash2","num_speculative_tokens":7,"draft_sample_method":"probabilistic","rejection_sample_method":"standard"}' \
    --compilation-config '{"pass_config":{"fuse_act_quant":true},"max_cudagraph_capture_size":64}' \
    --reasoning-parser qwen3 \
    --tool-call-parser qwen3_xml \
    --enable-auto-tool-choice

Step 5: Python, streaming, from your laptop

The server listens only on loopback, so open an SSH tunnel from your laptop and leave it running.

Any OpenAI SDK works; the client just needs some string as a key. If you ever bind to 0.0.0.0, vLLM's security guide says not to rely on --api-key alone: put a reverse proxy in front.

For scale: NVIDIA measured 37.29 tokens/s on long coding outputs. Your prompts will differ.

# on the laptop
ssh -N -L 8000:127.0.0.1:8000 you@spark-host
pip install openai
import time
from openai import OpenAI

client = OpenAI(base_url="http://localhost:8000/v1", api_key="unused")
MODEL = "nvidia/Qwen3.8-27B-NVFP4"

# 1 · stream tokens as they are decoded, and time the first one
t0 = time.time(); first = None
stream = client.chat.completions.create(
    model=MODEL, max_tokens=4096, stream=True,
    messages=[{"role": "user", "content": "Explain a KV cache in two sentences."}])
for chunk in stream:
    if chunk.choices and chunk.choices[0].delta.content:
        first = first or time.time()
        print(chunk.choices[0].delta.content, end="", flush=True)
print(f"\nTTFT {first - t0:.2f} s")

# 2 · rough tokens per second (includes prefill)
t = time.time()
r = client.chat.completions.create(model=MODEL, max_tokens=2048,
    messages=[{"role": "user", "content": "Write a Python LRU cache with tests."}])
print(r.usage.completion_tokens / (time.time() - t), "tokens/s")

Gotchas, collected

  1. Unified memory isn't a normal GPU. nvidia-smi --query-gpu memory fields read N/A; use plain nvidia-smi. Under pressure, flush the page cache: sudo sh -c 'sync; echo 3 > /proc/sys/vm/drop_caches'.
  2. A higher memory fraction isn't always better. 0.85 hung the Spark during autotune.
  3. Reasoning eats tokens. content: null with finish_reason: length means raise max_tokens.
  4. Context isn't free. At 32 KiB per token, eight 262K-token requests need about 69 GB of KV estimate.
  5. 0.0.0.0 means everyone. The recipe's default bind exposes an unauthenticated API. Use loopback and a tunnel, or a firewall and a proxy.
  6. Upgrades move flags. vLLM v0.33.0 ships CUDA 13.0 only and removed Medusa; v0.32.0 dropped Python 3.10. SGLang v0.5.22 needs Python 3.11+.
  7. Hybrid models confuse cache checks. SGLang's cached-token stays 0 for mamba/SSM hybrids; validate with a standard-attention model.
  8. Root-owned caches. SGLang's container writes weights as root, so deleting them needs sudo rm -rf.
